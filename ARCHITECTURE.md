# RuLeaks.Следопыт — архитектура

Веб-инструмент для HUMINT/OSINT-расследований: **Поиск** через API RuLeaks, **Досье** на персон и группы,
**Расследования** с графом связей, фактами и гипотезами. Вход — только через Telegram-бот RuLeaks,
доступ — по действующей подписке бота.

Статус: **прототип**. Каждый источник включается в `config.ini` флагом `enabled`:
- `[bot-db]` — **подключено**: подписка и токен API берутся из реальной базы бота (только чтение);
- `[api]` — **подключено**: поиск идёт в реальный dsstalker-api-gate;
- `[project-db]` — **подключено**: пользователи, сессии, история поиска, досье и расследования хранятся в PostgreSQL
  (`apps/server/src/adapters/postgres`); при `enabled = false` — в памяти с демо-данными.

Вход: бот пока не умеет подтверждать вход на сайт, поэтому на localhost работает dev-вход по Telegram ID
пользователя бота (`[server] dev-login`). Кроме входа через бота есть соло-режимы без него (`[config] auth`, §4.1). Все решения ниже отражены в коде каркаса.

## 1. Окружение: три системы

```
            ┌──────────────────────── браузер (SPA) ────────────────────────┐
            │ React · TanStack Router/Query · tRPC client · cookie ft_sid   │
            └───────────────────────────────┬───────────────────────────────┘
                                            │ /trpc  (только сюда)
                              ┌─────────────▼─────────────┐
                              │  apps/server (Node, BFF)   │
                              │  Fastify + tRPC            │
                              └──┬───────────┬──────────┬──┘
     SQL, роль только чтения     │           │ Bearer   │ SQL
       ┌─────────────────────────▼──┐  ┌─────▼────────┐ ┌▼──────────────────┐
       │ БД pyruleaks-bot           │  │ dsstalker-   │ │ PostgreSQL        │
       │ users · tokens · подписки  │  │ api-gate (Go)│ │ база ruleaks-     │
       │ site_login_requests (нов.) │  │ raw/deep/job │ │ foottracker       │
       └────────────────────────────┘  └──────────────┘ └───────────────────┘
          [bot-db]                         [api]            [project-db]
```

| Система | Владеет | Сайт обращается | Секция config.ini |
|---|---|---|---|
| **БД бота** | пользователи (`users`), токены (`tokens`), подписка (`users.subscribed_to`) | SQL, отдельная роль: `SELECT` на `users`/`tokens`, запись только в `site_login_requests` | `[bot-db]` |
| **dsstalker-api-gate** | поиск по утечкам, асинхронные задачи, кэш, троттлинг | HTTP с UUID-токеном пользователя в `Authorization` | `[api]` |
| **foottracker DB** | всё, что создаёт сайт: досье, медиа, расследования, доступы, снимки поиска | SQL (Drizzle), роль-владелец | `[project-db]` |

Правило: **таблицы бота сайт только читает.** Единственное исключение — `site_login_requests`, через которую
идёт вход. Логика подписки остаётся у бота: его миграция создаёт SQL-функцию `site_user_access(chat_id)`
с той же логикой, что `access_error()`, и сайт вызывает её, а не повторяет правила у себя.

## 1.1. Конфигурация

Один файл `config.ini` в корне репозитория (шаблон — `config.example.ini`, сам `config.ini` в `.gitignore`).
Его читает пакет `@ft/config`: сервер при старте и Vite (адрес API для прокси `/trpc`).

| Секция | Что задаёт |
|---|---|
| `[config]` | способ входа `auth` (`bot-db` / `none` / `password-sha256`), хеш пароля, соло-пользователь, раздел `geo-search` |
| `[server]` | адрес и порт, секрет cookie, срок сессии, `dev-login` |
| `[telegram]` | имя бота для ссылки входа |
| `[project-db]` | подключение к БД сайта |
| `[bot-db]` | подключение к БД бота (только чтение) |
| `[api]` | адрес API-шлюза, таймауты, интервал опроса задач, токен для соло-режима |
| `[geo-search]` | подложка карты поиска по геоданным: `raster` (публичные тайлы, разработка) или `pmtiles` (свои векторные), предел зума |

- Любой ключ переопределяется переменной окружения `FT_<СЕКЦИЯ>_<КЛЮЧ>`
  (`[project-db] password` → `FT_PROJECT_DB_PASSWORD`), путь к файлу — `FT_CONFIG`. Удобно для Docker и секретов.
- Значения проверяются Zod-схемой при старте; неизвестные секции и ключи выводятся предупреждением
  (опечатка не превращается молча в значение по умолчанию).
- У `[project-db]`, `[bot-db]`, `[api]` свой флаг `enabled`; выключенный источник заменяется имитацией
  (данные в памяти, демо-учётки, вымышленные результаты поиска). Включённый требует заполненных полей.
- Если `[server] host` — не localhost, обязательны `cookie-secret` (≥ 32 символов) и `dev-login = false`,
  а `auth = none` запрещён.
- В лог при старте выводится сводка подключений без паролей.

## 4. Авторизация через бота

Telegram Login Widget не используется: он требует `/setdomain`, и `oauth.telegram.org` у части пользователей из РФ
работает нестабильно. Два пути, оба без промежуточных сервисов.

### 4.0. Основной путь — подписанная ссылка из бота

Пользователь даёт боту команду (`/auth_foottracker`), бот присылает одноразовую ссылку на сайт; кто её откроет
в течение `[telegram] login-link-ttl-sec` (180 с), тот и входит. Подпись доказывает, что ссылку выдал бот, а
Telegram — что команду дал владелец `chat_id`. Ни API-сервера авторизации, ни таблицы в базе не нужно.

```
https://investigator.ruleaks.link/login?tg=<Telegram ID>&ts=<unix-секунды>&n=<случайная строка>&sig=<подпись>[&name=<имя>][&nick=<ник без @>]

подпись:  sig = base64url( HMAC-SHA256( login-secret, tg + "\n" + ts + "\n" + n + "\n" + name + "\n" + nick ) )  без «=»
          (name и nick — как в ссылке; отсутствующие — пустые строки)
n:        8–64 символов [A-Za-z0-9_-], случайные (16 байт в base64url); у каждой ссылки свой
секрет:   [telegram] login-secret на сайте = такой же ключ в конфиге бота; не короче 32 символов
```

Сайт (`auth.loginWithLink`, `adapters/login-link.ts`): сверяет подпись первой (`timingSafeEqual`), затем срок
(`ts` не старше TTL и не больше чем на минуту в будущем), затем одноразовость (пара `tg:n` помнится в памяти до
истечения срока) — и только потом делает upsert пользователя (имя и ник из ссылки, если бот их передал), читает
подписку из базы бота и ставит cookie сессии. Страница `/login` открыта без сессии; после входа она переходит в
поиск с заменой адреса в истории. Ошибки: `BAD_LINK`, `LINK_EXPIRED`, `LINK_USED`, `LINK_LOGIN_DISABLED` (секрет
не задан). Проверить без бота: `npm run login-link -- <Telegram ID> [имя] [@ник]`.

Бот должен отправлять ссылку с выключенным превью (`disable_web_page_preview` / `LinkPreviewOptions(is_disabled=True)`):
иначе сервер превью Telegram откроет одноразовую ссылку первым. На стороне Python:

```python
import base64, hmac, hashlib, secrets, time, urllib.parse
def login_link(secret: str, site: str, tg_id: int, name: str = "", nick: str = "") -> str:
    ts, n = str(int(time.time())), base64.urlsafe_b64encode(secrets.token_bytes(16)).rstrip(b"=").decode()
    payload = "\n".join([str(tg_id), ts, n, name, nick]).encode()
    sig = base64.urlsafe_b64encode(hmac.new(secret.encode(), payload, hashlib.sha256).digest()).rstrip(b"=").decode()
    q = {"tg": tg_id, "ts": ts, "n": n, "sig": sig, **({"name": name} if name else {}), **({"nick": nick} if nick else {})}
    return f"{site}/login?{urllib.parse.urlencode(q, quote_via=urllib.parse.quote)}"   # пробел → %20, не «+»
```

### 4.1. Запасной путь — deep-link с подтверждением в боте (код есть, бот пока не подтверждает)

```
браузер              сайт (BFF)                         БД бота / бот
  │ auth.start ───────▶ INSERT site_login_requests ──────▶ nonce, TTL 5 мин
  │ ◀── deepLink t.me/<bot>?start=login_<nonce> + QR
  │ ◀── Set-Cookie ft_login = HMAC(nonce) (httpOnly, TTL 5 мин)
  │ (пользователь в Telegram) ──────────────────────────▶ бот: /start login_<nonce>
  │                                                       кнопка «Войти на сайт» → confirmed, tg_id
  │ auth.status (опрос 1.5 с) ─▶ cookie ft_login сходится с nonce? иначе «expired», nonce не расходуется
  │                              SELECT site_login_requests
  │                            ◀── confirmed + tg_id
  │                            consume; upsert user; сессия
  │ ◀── Set-Cookie ft_sid (httpOnly, Secure, SameSite=Lax, signed)
```

Nonce виден всем, кто видит экран или ссылку (QR-код, чат с ботом), поэтому сессию получает только браузер,
начавший вход: `auth.status` требует cookie `ft_login`, выданную `auth.start` для этого nonce.

- Сессия хранится на сервере (`sessions`, в БД — sha256 от значения cookie), срок — `[server] session-ttl-days`.
  JWT не используем: сессию нужно уметь отозвать сразу (команда бота «Завершить все сессии на сайте»).
- **Контроль подписки** — `SELECT * FROM site_user_access(<tg_id>)` в БД бота (ответ кэшируется на 60 с).
  Неактивная подписка переводит сайт в **режим чтения**: свои и расшаренные объекты видны,
  поиск и любые изменения запрещены (`activeProcedure` → `FORBIDDEN SUBSCRIPTION_INACTIVE`).
  Баннер в интерфейсе ведёт в бота для продления; есть кнопка «проверить снова».
- **Токен шлюза** пользователя (`tokens.token` по `users.tokenid`) сервер читает из БД бота при каждом поиске
  и никогда не отдаёт в браузер. Копию у себя не хранит.

### 4.2. Соло-режимы без бота

`[config] auth` выбирает способ входа; `bot-db` — описанный выше. Два других — для работы одного человека,
без бота и подписки (`apps/server/src/adapters/solo.ts`, `SoloBridge` вместо моста к боту):

- `none` — входа нет: каждый запрос выполняется от имени соло-пользователя. Только на localhost.
- `password-sha256` — один пользователь, `auth.password` сверяет sha256 пароля с `[config] password-sha256`
  (`timingSafeEqual`; ≤ 5 неудач в минуту с адреса, каждая с задержкой). Хеш подмешан в секрет подписи cookie —
  смена пароля завершает все сессии; сессии других пользователей (оставшиеся от входа через бота) не принимаются.
  Хеш без соли — пароль должен быть длинным и случайным.

Соло-пользователь — обычная запись `users` с `[config] user-tg-id` / `user-name` (создаётся при старте):
указав свой Telegram ID, человек видит объекты, созданные при входе через бота. Подписка всегда активна,
токен шлюза — `[api] token`; `[bot-db]` и `dev-login` не используются. Процедуры входа через бота отвечают `NOT_FOUND`,
веб узнаёт режим из `auth.mode` (форма пароля вместо ссылки в бота, без кнопки «Выйти» при `none`).

### Что добавить в бота

1. **Команда входа** (сначала в админ-боте `pyruleaksadmin-bot`, затем в `pyruleaks-bot`): `/auth_foottracker`
   собирает ссылку по 4.0 (`login_link(secret, site, chat_id, имя, ник)`) и отправляет её без превью. Секрет и адрес
   сайта — в конфиге бота. Больше ничего: ни таблиц, ни HTTP.
2. (Позже, для 4.1) миграция alembic с `site_login_requests` и `site_user_access()`, обработчик `/start login_<nonce>`

3. (Позже) команда «Завершить все сессии на сайте» — отметка, которую сайт проверяет при обращении к сессии.

## 5. Поиск

Три раздела повторяют меню бота. Каталоги путей и параметров — в `packages/shared/src/search.ts`
(сверены с `app/api/endpoints.py` и `app/api/client.py` бота):

| Раздел | Маршрут | Команда бота | Что ищет |
|---|---|---|---|
| Поиск по атрибутам | `/search` | `/search`, `/deepsearch` | 18 видов: телефон, email, ФИО+дата, документы, авто, Telegram ID… raw или deep |
| Поиск в Telegram | `/search/telegram` | `/tgsearch` | комментарии, реакции, ответы пользователя и ему, активность по месяцам и часам, полнотекстовый поиск (`/tgcmnts/v1/*`) |
| Нечёткий поиск | `/search/fuzzy` | `/regsearch` | маска email (`emailmask`), маска госномера (`platemask` + `vehicpart`) |

- В Telegram-поиске пользователь задаётся ID, @ником или телефоном — сервер разрешает его, как бот
  (`_parse_identifier`): ник → `search_ids.bynik`, телефон → raw-поиск по телефону и первый `tgids`.
  Если ник принадлежит нескольким ID, задача получает состояние `choose` и интерфейс предлагает выбрать.
- Маски проверяются до отправки так же, как в шлюзе (`checkGlobMask`, `checkVehicPart`); латиница
  в госномере заменяется кириллицей.
- История ведётся по каждому разделу отдельно и очищается кнопкой в блоке «История».
- Комментарии Telegram переносятся в досье заметками-цитатами (источник — ссылка на сообщение),
  найденные Telegram ID — атрибутами.
- **Сервер — посредник.** `search.start` вызывает шлюз с токеном пользователя. Если ответ пришёл
  в синхронное окно (2 с), задача сразу `done`. Иначе сохраняется `gatewayJobId`, и `search.job` опрашивает
  `job.results` при каждом запросе клиента (позже — SSE и фоновый опрос через pg-boss).
- **Снимки.** Шлюз хранит результат 1–15 минут, поэтому сайт сохраняет каждый результат в `search_snapshots`.
  Снимок, прикреплённый к досье или факту, становится постоянным (`pinned`); остальные чистятся через N дней.
- В интерфейсе любое найденное значение можно отметить для досье или сделать следующим шагом поиска
  (молния ⚡: телефон → поиск по телефону и т. д.). Перенос в досье создаёт атрибуты с источником
  `search:<snapshotId>` и элемент «снимок поиска».

### 5.1. Поиск по геоданным

Раздел `/search/geo` включается флагом `[config] geo-search`. Если флаг выключен, `geo.config` возвращает `null`:
пункта меню нет, страница пишет «выключен», маршруты `/geo/*` не регистрируются. Область — точка (щелчок или
перетаскивание маркера, поля Latitude/Longitude) и радиус в км (до 50 — предел шлюза). Поиск — отдельный раздел
истории `geo` (`search.start` с `section: 'geo'`) → `/ruleaks/v1/raw_search.byloc_radius?lat=&lon=&radius=<метры>`;
ответ того же вида, что у raw-поиска по атрибутам, и показывается тем же `JobView`. Запрос в истории и в `?q=` —
«широта, долгота @метры», как значение `geolocs`.

- **Карта — MapLibre GL** (`features/search/GeoPicker.tsx`), а не Leaflet: она рисует векторные тайлы, а это нужно
  для своей подложки. Круг строится многоугольником по большим кругам, поворот и наклон карты выключены.
  Воркер MapLibre подключается через `?worker&url` + `setWorkerUrl`: сам он ищет файл по `import.meta.url`, а после бандлинга Vite файла там нет.
- **Подложка** (`[geo-search] tiles`):
  - `raster` — публичные растровые тайлы, затемнённые paint-свойствами слоя (`raster-brightness-min > max` инвертирует яркость).
    Только для разработки: правила tile.openstreetmap.org и утечка просматриваемых районов стороннему серверу.
  - `pmtiles` — вырезка Европы и России из сборки Protomaps (`tools/geo/`), зум до 14; стиль — `@protomaps/basemaps`
    (тёмная схема, подписи на `lang`). Отдельного тайл-сервера нет: сервер приложения отдаёт файл `.pmtiles` и `basemaps-assets`
    по `/geo/tiles.pmtiles` и `/geo/assets/*` (`geo-files.ts`, `@fastify/static` с `serve: false`), только при наличии
    сессии. Браузер читает файл Range-запросами (протокол `pmtiles://`). Вместо путей можно указать https-адреса
    Protomaps — это для проверки в разработке.

### 5.2. Сканы документов

В записях утечек шлюз отдаёт ключ `scans` — uuid сканов в хранилище scanstore-api-gate (`[scanstore-api]`).
Это не атрибут: «Поиск по атрибутам» показывает их отдельным боксом с превью, клик открывает скан целиком.
Браузер не ходит в хранилище: токен хранилища — один на сайт, поэтому картинки проксирует сервер
(`/scans/<uuid>`, только при наличии сессии; ETag и 304 пробрасываются), а тип документа, номер и владельца
отдаёт `scans.meta` без `metainfo` (OCR-текст). Сканы неизменяемы — метаданные кэшируются в памяти без срока.
Если `[scanstore-api] enabled = false`, `scans.config` возвращает `null`, маршрут не регистрируется и бокса нет.

### 5.3. Поиск личных страниц

Раздел `/search/pages` (флаг `[config] pages-search`, по умолчанию включён): по **нику или e-mail** сервер проверяет,
есть ли у человека страница или регистрация на сотнях сайтов. Это перенос на TypeScript логики трёх OSINT-проектов
(`apps/server/src/pages/`). Запрос разбирает `parsePagesQuery` (`@ft/shared`): e-mail ищется и как почта, и по нику из
части до `@` (`user+метка@…` → `user`); всё остальное — ник.

- **По нику — [Sherlock](https://github.com/sherlock-project/sherlock).** Список сайтов — его `data.json` без изменений
  (`sites.json`, MIT; обновляется `npm run pages-sites-update`), вердикт — `checkSite` в `check.ts` (`errorType`: строка
  в ответе / код ответа / редирект; `regexCheck`; отпечатки защиты от ботов).
- **По e-mail — [holehe](https://github.com/megadose/holehe) + [blackbird](https://github.com/p1ngul1n0/blackbird).**
  Идея обоих: дёрнуть форму регистрации или восстановления пароля сайта с адресом и по ответу понять, занят ли он.
  Список — `email-data.json` blackbird без изменений (`email-sites.json`, обновляется `npm run pages-email-update`),
  разбирается в `email-sites.ts`, туда же в коде (`EXTRA`) добавлены проверки в стиле holehe, которых у blackbird нет
  (например, Mail.ru). Вердикт — `checkEmailSite` в `check.ts` (код+строка «занят», код+строка «свободен»,
  преобразование адреса `sha256`, предварительный запрос за cookie). Новые модули holehe добавляются записями в `EXTRA`.
  Плейсхолдер `{account}` подставляется с кодированием по месту (адрес и form-тело — percent-кодирование, JSON-тело —
  экранирование строки), иначе `user+tag@…` превращался бы в `user tag@…`.
- **Пробы с побочным действием** — настоящая форма регистрации (в теле пароль) или восстановления пароля — помечаются
  `sideEffect` и по умолчанию не выполняются (`[pages-search] side-effect-probes`): если адрес свободен, сайт заведёт
  учётку на цель или напишет ей, раскрыв интерес к адресу. Проверки holehe, которые только спрашивают сайт, остаются.

- **Внутренняя сеть закрыта** (`pages/outbound.ts`): редиректы следуются вручную (не больше 5), каждый адрес цепочки
  должен быть http(s) и вести на публичный IP — буквальный или по DNS; loopback, частные, link-local (метаданные
  облака) и CGNAT-диапазоны отвергаются. Сайт из манифеста не может перенаправить сервер на localhost или базу.
- **Запросы делает сервер**, не браузер (CORS), с User-Agent Firefox. Один поиск по e-mail — это и проверки по почте, и
  поиск Sherlock по нику из адреса; по `concurrency` параллельно с таймаутом `timeout-sec` на сайт ([pages-search]);
  на пользователя — один поиск одновременно (новый останавливает прежний), на процесс — `MAX_RUNNING`, иначе `PAGES_BUSY`.
- **Чем найдено** — у каждого результата `by` (`username` / `email`); в интерфейсе это метка «по нику» / «по e-mail»,
  и она же попадает в примечание источника при переносе в досье.
- **Задание — в памяти сервера** (`jobs.ts`), не в `search_jobs`: это не поиск в утечках, результат — список ссылок.
  Завершённые задания живут час и образуют «Историю» раздела; перезапуск их забывает. Браузер опрашивает `pages.job`
  раз в секунду; пока идёт поиск, приходят только найденные, полный список — по окончании.
- **Вердикты эвристические**: сайт, отвечающий 200 на любой ввод, даёт ложное «найдено»; поэтому в карточке есть ссылка
  — проверить глазами. Списки сайтов стареют, их нужно периодически обновлять из upstream.
- Под строкой поиска — «inspired by Sherlock, holehe, blackbird».

### 5.4. Окно длительного процесса

Длительные операции (поиск личных страниц, экспорт в файл и PDF, импорт, PDF-отчёт поиска в Telegram) показывают
модальное окно процесса `components/ProgressDialog.tsx`: шкала (доля выполненного или бегущая полоса, если
длительность неизвестна), строка состояния, прошедшее время, «Отмена». Окно нельзя закрыть щелчком мимо — только
отменить (Esc = отмена). Для заданий на сервере окно питается опросом (`pages.job`), для асинхронного кода в браузере —
`useProcess()`: `run()` показывает окно на время промиса, `p.set()` двигает шкалу, `p.signal` передаётся в tRPC-запросы
через vanilla-клиент (`utils.client.….mutate(input, { signal })`) — отмена обрывает ожидание ответа; серверная часть
экспорта при этом доработает впустую, запись импорта в базу не прерывается.

## 6. Досье

- Виды: **персона** и **группа лиц**. Группа ссылается на досье участников, а не копирует их.
- Элементы досье — `attribute | link | media | note | snapshot | post` (discriminated union в `@ft/shared`).
  `post` — посты, комментарии, ответы и реакции персоны в соцсетях (бокс «Посты и реакции» у досье персоны);
  отмеченные сообщения «Поиска в Telegram» переносятся в досье постами, `extId` не даёт перенести одно сообщение дважды.
  Порядок задаётся `position`, медиа переставляются перетаскиванием.
- **Видимость досье: только `private | shared`.** Публичных досье нет: в них персональные данные из утечек.
- Сводка и заметки хранятся в Markdown. Упоминание: набрать `@` → выбрать досье → в текст вставляется
  обычная ссылка `[@Название](/dossiers/<id>)`. Свой синтаксис не нужен, текст читается где угодно.
- **Медиа (план):** presigned PUT в S3 → запись `media` → задача pg-boss: превью (`sharp`), sha256
  (дедупликация), EXIF/GPS сохраняется как улика. В прототипе файл встраивается как data URL.

## 7. Расследования

- **Связи** — граф React Flow. Узлы: персона, организация, событие, место, объект, документ.
  Узел-персона ссылается на досье (двойной клик открывает его). Связь хранит тип (`руководит`, `знакомы`…),
  пояснение, достоверность и подтверждающие факты. Стиль линии зависит от достоверности:
  сплошная — подтверждено, пунктир — сомнительно.
- Граф сохраняется **целиком** с задержкой 1,2 с после последней правки, с номером версии
  (оптимистичная блокировка: при конфликте сервер отвечает `CONFLICT`, клиент перечитывает данные).
  Для совместной работы в реальном времени позже подключить Yjs + Hocuspocus. Модель данных менять не придётся.
- **Факты** — хронология. Каждый факт: Markdown-текст, дата, источники с оценкой, привязка к узлам.
- **Гипотезы** — упрощённый ACH (анализ конкурирующих гипотез): каждый факт помечается как
  «подкрепляет» или «противоречит», статус: открыта → подкреплена → подтверждена / опровергнута.
- Видимость: `private | shared | public`. Публичное расследование открывается **без входа**, но
  сервер скрывает список доступов и ссылки на досье, которые читатель не может открыть (`present()`).

## 7.1. Экспорт и импорт файла

Кнопка «Файл» у досье и расследования открывает окно: автор (по умолчанию — имя пользователя), примечание,
необязательный пароль, опция «доступно редактирование» (пока только пометка в `meta.info`). Экспортировать может
любой, кто может читать объект, в том числе без активной подписки. Файл собирает сервер
(`apps/server/src/export/build.ts`, процедуры `dossiers.exportFile` / `investigations.exportFile` — мутации, чтобы
пароль не попал в URL) и отдаёт ZIP в base64; расширение `.ftx`. Формат описан Zod-схемами в
`packages/shared/src/export.ts` — по ним будет проверяться импорт.

- **Версия** — файл `version.v1` (строка текста) без шифрования: версию видно, не зная пароля.
  Остальное (`meta.info`, `dossiers/d1.json`, `investigations/i1.json`, `relations.json`, `searches/s1.json`,
  `media/m1.jpg`) зашифровано AES-256 (WinZip AE-2, `@zip.js/zip.js`).
- **Пароль архива ≠ пароль экспорта**: PBKDF2-HMAC-SHA256 (600 000 итераций, соль — константа в коде) от
  введённого пароля (`export/password.ts`). Без пароля ключ выводится из пустой строки: файл всё равно зашифрован,
  но его откроет любая установка Следопыта. Соль и итерации — часть формата; их смена = `version.v2`.
- **Без идентификаторов базы**: объекты ссылаются друг на друга ключами внутри файла (`d1`, `n1`, `f1`, `s1`…),
  теги — текст + цвет, типы связей — текст, картинки из data URL — файлы `media/` (одинаковые — один файл).
  Ссылки `[@Имя](/dossiers/<id>)` в Markdown становятся `[@Имя](ft:d1)`, ссылки на досье вне файла — текстом.
  Пользователи и доступы не экспортируются.
- **Что входит**: у досье — оно само, участники группы и связанные персоны (полностью, один уровень); у
  расследования — граф, факты, гипотезы и досье узлов. Связи между персонами — только между вошедшими досье.
  Всё — только то, что экспортирующий может читать; снимки поиска — только свои (как и в интерфейсе).
- **Сквозной `uid`** у досье и расследования (колонка `uid`, не первичный ключ) пишется в файл. У импортированной
  копии он тот же, что у оригинала, поэтому повторный импорт узнаёт объект. Уникален среди живых объектов одного владельца.

**Импорт** — кнопка «Импорт» в списках досье и расследований (файл любого из двух видов). Три шага
(`routers/imports.ts`): `upload` — файл частями в base64 (каждая меньше `bodyLimit`), хранится в памяти сервера
до 30 минут (`export/uploads.ts`); `inspect` — версия по `version.vN`, расшифровка (сначала введённым паролем,
потом пустым; ошибки `NEED_PASSWORD` / `BAD_PASSWORD`), проверка Zod-схемами и пробное преобразование (картинки
при этом не кодируются в data URL), ответ — что в файле и какие объекты уже есть у пользователя; `commit` — запись
(`export/import.ts`).
- Память: до записи файл живёт в процессе в нескольких видах (части, склеенный буфер, извлечённые картинки),
  поэтому лимиты жёсткие — файл до 64 МБ, один незавершённый импорт на пользователя (новый вытесняет прежний),
  общий потолок 256 МБ на процесс (`IMPORT_BUSY` — повторить позже). Настоящие файлы экспорта — единицы-десятки МБ.
  Потоковая загрузка на диск и файловое хранилище медиа сняли бы лимиты, но это отдельный этап (см. «Медиа (план)»).
- Объекты сопоставляются по `uid` среди **своих** живых объектов: нашёлся — содержимое **перезаписывается целиком**
  (интерфейс заранее предупреждает и перечисляет такие объекты; видимость и доступы остаются), нет — создаётся новый
  приватный объект с тем же `uid`. Чужие копии (расшаренные мне) не перезаписываются — создаётся своя.
- Теги — из словаря импортирующего по тексту, недостающие заводятся с цветом из файла; типы связей — так же.
  Связи между персонами файла у перезаписанных досье заменяются файловыми, связи с досье вне файла остаются.
- Снимки поиска — скрытые (`hidden_at`) закреплённые записи истории; такой же снимок пользователя (раздел, вид,
  запрос, время) переиспользуется. Изображения из `media/` снова становятся data URL.
- Импорт не атомарен (каждый объект — своя транзакция), но повторный импорт того же файла доделает прерванный:
  уже созданное найдётся по `uid`. Опция «доступно редактирование» только показывается.

## 7.2. Отчёт в PDF

Кнопка «PDF» у досье и расследования — то же окно, что у экспорта в файл (автор, примечание, необязательный пароль),
с опциями: фото и изображения, источники с оценкой, связанные досье отдельными разделами (у досье — участники группы
и связанные персоны, у расследования — досье узлов графа). Отчёт собирает сервер (`apps/server/src/pdf/`,
процедуры `dossiers.exportPdf` / `investigations.exportPdf`), pdfmake со шрифтом Roboto из пакета (кириллица есть,
эмодзи нет — они вырезаются).
- Вёрстка — в отдельном потоке (`pdf/worker.ts`, worker_threads; очередь и жизненный цикл — `pdf/render.ts`):
  pdfmake раскладывает документ синхронно и на тысячах сообщений занимает процессор десятками секунд, в главном
  потоке это останавливало бы все запросы. Главный поток собирает только содержимое (`Content[]`), которое уходит в
  воркер через structuredClone — поэтому в нём нет функций: раскладки таблиц заданы по имени (`pdf/theme.ts`),
  колонтитул и правила переноса страниц воркер добавляет сам. Один воркер на процесс, задания по очереди,
  остановка после 5 мин простоя, предел 10 мин на отчёт.
- Markdown переводится в блоки pdfmake (`pdf/markdown.ts`, лексер `marked`); упоминание `[@Имя](/dossiers/<id>)`
  становится ссылкой на раздел этого досье внутри PDF, если он есть.
- Граф расследования — SVG по сохранённым координатам узлов (`pdf/graph.ts`), стиль линии по достоверности, как в
  редакторе; факты нумеруются хронологически, связи и гипотезы ссылаются на их номера.
- Снимков поиска в отчёте нет (нужное из них уже в атрибутах). Изображения — только data URL в JPEG, PNG или SVG;
  внешние адреса и локальные файлы pdfmake открывать запрещено (`setUrlAccessPolicy` / `setLocalAccessPolicy`).
- Пароль — штатное шифрование PDF (AES-256, PDF 1.7 ext 3); без пароля PDF не шифруется. Даты — в часовом поясе
  браузера, время постов — в UTC (как в интерфейсе).

## 8. Оценка источников

У каждого атрибута, заметки, медиа и факта есть `source`: тип (`search`, `url`, `humint`, `document`,
`manual`), ссылка или псевдоним источника и оценка по **системе Адмиралтейства (NATO)**:
надёжность источника **A–F** и достоверность сведений **1–6**. В интерфейсе это бейдж `B2`
с цветом и подсказкой. Стандарт HUMINT-аналитики позволяет отделять проверенное от слухов.

## 9. Доступ

- Роли: `owner` · `editor` · `viewer`. Поделиться можно по Telegram `@username`. Получатель должен
  хотя бы раз войти на сайт.
- Все проверки прав — в `apps/server/src/authz.ts` (`can(user, 'read'|'edit'|'manage', obj)`).
  Чужой недоступный объект неотличим от несуществующего (`NOT_FOUND`).
- `manage` (видимость, доступы, удаление) — только владелец.
- План: RLS в Postgres как второй рубеж; таблица `audit_log` для поисков и открытия чужих объектов.

## 10. Модель данных

Источник истины — SQL-миграции в `packages/db/migrations` (node-pg-migrate, аналог alembic; описание и
команды — `packages/db/README.md`). Первая версия — `20261004120000_initial-schema.sql`, теги —
`20261005120000_tags-dictionary.sql`:

```
users(id, tg_id, display_name, username)                     sessions(id_hash sha256, user_id, expires_at)
dossiers(id, uid, owner_id, kind, title, summary_md, visibility, cover_media_id, version, deleted_at, search_tsv)
dossier_members(group_id, member_id, role_label)             dossier_items(id, dossier_id, type, data jsonb, source jsonb, position, media_id)
dossier_shares(dossier_id, user_id, role)                    media(id, owner_id, storage_key, sha256, exif)
search_jobs(id, user_id, section, kind, query, params, state, result jsonb, pinned, hidden_at)
investigations(id, uid, owner_id, title, description_md, visibility, version, deleted_at, search_tsv)
investigation_shares(investigation_id, user_id, role)
graph_nodes(id, investigation_id, type, label, dossier_id, props, x, y)
graph_edges(id, investigation_id, source_node_id, target_node_id, relation, label, credibility)
facts(id, investigation_id, text_md, occurred_at, sources jsonb)   fact_nodes(fact_id, node_id)   edge_facts(edge_id, fact_id)
hypotheses(id, investigation_id, title, text_md, status)     hypothesis_evidence(hypothesis_id, fact_id, stance)
revisions(object_type, object_id, version, diff)             audit_log(user_id, action, object_type, object_id, meta, ip)
tag_texts(id, text)  tags(id, owner_id, text_id, color)  dossier_tags(dossier_id, tag_id, position)  investigation_tags(…)
relation_texts(id, text)  relation_types(id, owner_id NULL=предопределённый, text_id)  dossier_relations(id, from_id, to_id, type_id, from_note, to_note)
```

- Теги — словарь: тексты (`tag_texts`, всегда заглавными) общие для всех, а словарь у каждого свой (`tags`: текст +
  цвет фона), и видит человек только свои теги. На объект ставится тег из словаря того, кто его поставил, — у
  соавторов он показывается с цветом автора; править тег может только владелец словаря, снять с объекта — любой
  редактор. Удаление тега из словаря снимает его со всех объектов.
- Связи между персонами — `dossier_relations`: связь хранится один раз (from → to) и показывается в обоих досье;
  между двумя персонами несколько связей разных типов. Тип общий, пояснение — своё у каждой стороны (`from_note` в досье
  from_id, `to_note` в досье to_id: «родственник · сын» / «родственник · отец»). Типы — словарь как у тегов
  (тексты общие, в нижнем регистре; свой тип виден автору), плюс предопределённые (`owner_id IS NULL`): родственник,
  совместная работа / учеба / служба. Другая персона показывается, только если её досье можно читать.
- Идентификаторы — `uuidv7()` (PostgreSQL 18): упорядочены по времени, индексы растут без фрагментации.
- Доступы — две таблицы (`dossier_shares`, `investigation_shares`) с настоящими внешними ключами, а не одна полиморфная.
- JSONB — для гибких частей (тело элемента досье, источники, props узла, ответ шлюза); то, по чему ищут
  и фильтруют, — в колонках. GIN по `dossier_items.data` — поиск совпадений между досье («где ещё этот телефон»).
- Поиск по своим объектам: сгенерированные `search_tsv` (`russian`), нечёткий по названию досье — `pg_trgm`.
- Досье и расследования удаляются мягко (`deleted_at`); вложенное — `ON DELETE CASCADE`.

## 11. Безопасность

- `noindex, nofollow` на всём сайте; публичные расследования открываются только по ссылке.
- Cookie: httpOnly, Secure, SameSite=Lax, подписанная (`[server] cookie-secret`). tRPC-мутации идут POST с JSON, а CORS закрыт:
  фронт и API на одном origin.
- Ограничения ввода — Zod-схемы (длины, количество узлов графа ≤ 2000, связей ≤ 5000).
- (план) Rate-limit на `auth.start` и `search.start` (`@fastify/rate-limit`), поверх троттлинга шлюза.
- Пароли БД и секрет cookie — только в `config.ini` (вне git) или в переменных окружения `FT_*`.

## 12. Развёртывание (план)

Docker Compose: `caddy` (TLS, статика `apps/web/dist`, прокси `/trpc`, `/geo` и `/scans` → server) + `server` + `minio`.
Файл тайлов карты (`.pmtiles`, десятки ГБ) и `basemaps-assets` лежат на том же хосте, что и сервер (`tools/geo/README.md`).
Postgres — существующий кластер, отдельная база и роль `ruleaksfoottracker` (скрипт `packages/db/sql/000_create_database.sql`).
